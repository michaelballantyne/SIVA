# Hot-reload simplicity review — 2026-04-26

> **Update 2026-04-26 (post-`1b02c82`):** all five proposed simplifications
> shipped. `BuildCoordinator` now uses a single `Condition`, the
> `_pending_*` triplet collapsed into one `BuildRecord` slot,
> `BuildRecord.code` is gone, `save_version` moved onto `ViewContext`, and
> `ctx.applied_hash` is the "renderer reflects hash X" fact described in
> the closing section.

Lens: harshest possible read for elegance. The feature works and the tests
exercise it, but the design has accumulated more moving parts than the problem
needs. Top opportunities below; the staleness/double-build/orphan list at the
bottom suggests the design is fighting itself.

## Simplifications worth doing (priority order)

1. **Collapse three sync primitives into one `Condition`.** Today we have
   `BuildCoordinator._lock`, `_work_event`, and per-record `BuildRecord._done_event`.
   A single `threading.Condition` (with `_lock` as its lock) replaces both
   events: workers `wait_for(lambda: self._pending or self._shutdown)`, and
   waiters `wait_for(lambda: record.status != "running")`. `request_build` /
   `_run_build` end with `cond.notify_all()`. This kills `_done_event`,
   `_work_event`, `BuildRecord.wait()`, and `_finish()`, and fixes the
   "orphaned pending stays running forever" race for free — when a pending
   record is replaced, you can mark it `status="cancelled"` and `notify_all`,
   and any waiter unblocks with the right answer.

2. **Stop carrying both `_pending_*` triplet and `_inflight`. Use a queue.**
   `_pending_hash`, `_pending_code`, `_pending_record` are three fields that
   redundantly encode one record. Replace the triplet with `_pending: Optional[BuildRecord]`
   (code and hash are already on it). Better: use a 1-slot queue
   (`_pending` is at most one record; new request *replaces* the slot, marking
   the displaced record cancelled). This is exactly the semantics described
   in the docstring; the current code spells it out longhand.

3. **Drop `code` from `BuildRecord`.** `record.code` is read once, in
   `_run_build`, by going through `record.code`. The triplet already passes
   it implicitly. Once #2 is done, the record holds its own code; once #2 is
   *not* done, the field is dead — `_worker_loop` reads `code` from
   `_pending_code`, not the record.

4. **Inline `_take_screenshot` and fold `_save_version_for` into ViewContext.**
   `_take_screenshot` is two lines wrapping `renderer.render(); return renderer.screenshot(p)`.
   Module scope + lambda indirection earns nothing. `_save_version_for`
   mutates `ctx.version`, writes `ctx.history_dir`, and lives at module scope
   touching ctx internals — it is a `ViewContext.save_version(code, screenshot)`
   method in disguise. Putting it on `ViewContext` also clarifies that
   versioning is per-view state, not coordinator state.

5. **Lifecycle: stop having `ViewContext.__init__` start threads.** Today
   construction silently spawns a worker thread and a watchdog observer.
   `_init_for_test` hits this path, so every test gets a real watchdog and
   build worker, even ones that never touch hot-reload. Either:
   (a) make `ViewContext` plain data and have `main()` / `new_view()` call
   `ctx.start_hot_reload()` explicitly, or (b) at minimum, skip watcher start
   when `pipeline_file` doesn't exist. Right now `_NoOpRenderer` tests carry
   live OS threads they don't know about.

## Things that look ugly but should stay

- **Status file written to disk every build.** Feels redundant with the
   in-memory `BuildRecord`, but it's the only signal that survives an MCP
   client crash or out-of-process tooling. Keep.

- **Two-phase render (compute on worker, apply on main thread).** The
   `run_on_main_thread` hop looks heavy, but VTK + Cocoa requires it. The
   ugliness is intrinsic to the platform.

- **SHA-256 keying instead of mtime.** mtime would be one line; the hash
   correctly handles "save the same content twice" and "atomic rename to
   identical bytes." Performance is invisible at file sizes we care about.

- **Debounce in the watcher.** 100ms looks like a magic number, but editors
   genuinely emit duplicate events on save. Removing it produces duplicate
   builds in the common case.

## Where the design is fighting the requirements

The three races in the implementer's notes are not three independent bugs
— they are one bug seen from three angles: **`BuildRecord` is being asked
to be both an event ("a build with this hash happened") and a cache entry
("the renderer currently reflects this hash").** Sharing finished records
caused the staleness race; *not* sharing them caused the double-build race;
the orphaned-pending race is the same confusion at queue level.

The right model is: there is **one** "renderer reflects hash X" fact per view
(call it `ctx.applied_hash`), and builds are events that update it. Then
`wait_for_current` is trivially: if `applied_hash == current_hash` and no
build is in flight, return; else ensure a build is running and wait. No
caching of finished records, no idempotency special case, no orphaned
pending pathology — just an applied-state field plus a single in-flight
slot. This is the simplification that would make #1–#3 above compose
cleanly. I'd do it before the others.
