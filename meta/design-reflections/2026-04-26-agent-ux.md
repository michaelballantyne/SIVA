# Agent UX after hot-reload + incremental rebuild

**Date:** 2026-04-26

The contract of `run_pipeline` quietly changed: it no longer "executes the
pipeline" — it waits for whatever the file watcher and build coordinator
already started. None of the agent-visible surfaces (docstrings,
`FastMCP(instructions=...)`, `get_dsl_overview`) say this clearly. An agent
that doesn't know hot reload is on will still call `run_pipeline()` after
every edit, which works (it short-circuits via `_latest`) but obscures the
new mental model and makes `pipeline_status` look pointless.

This reflection focuses on the smallest set of docstring/instruction edits
that make the new model legible.

## 1. Docstring changes

### `run_pipeline` (server.py:478)

Current opening line and final note:

> Execute the current view's pipeline file. Clears the scene and rebuilds from scratch.
> ...
> Hot reload: the server watches view-<name>.py and rebuilds in the
> background whenever the file is saved. run_pipeline() waits for the
> build matching the current file content and returns its result.

The hot-reload note is buried at the bottom and the lead is wrong (it isn't
the file save that "executes" anymore). Proposed replacement for the opening
paragraph and the Notes block:

> Wait for the current view's pipeline file to finish building, and return
> the build report plus a screenshot.
>
> The server watches `view-<name>.py` and starts a rebuild automatically
> every time the file is saved (debounced ~100ms). You do not need to call
> `run_pipeline()` to "kick" a build — saving the file is enough. Call
> `run_pipeline()` when you want to **block until the build of the current
> file content is done** and see the result. If a matching build has already
> finished, this returns immediately (no rebuild).
>
> Builds are incremental, keyed on a content hash of each DSL node:
>   - Visual-only edits (colormap, opacity, scalar_range, camera) — ~free,
>     all cache hits, ~1ms.
>   - Mid-pipeline edits (a threshold range, a contour value) — only that
>     node and its downstream rebuild; ~10–50ms typical.
>   - Changing the data file or `source(...)` arguments — full rebuild.
>
> Notes:
>   - Every successful build saves a versioned snapshot to
>     `.vislang/history/<view>/`. Use `list_versions()` / `restore_version()`.
>   - Use `pipeline_status()` for a non-blocking peek (no screenshot, no wait)
>     while iterating on the file.
>   - The status file `view-<name>.status.json` (next to the pipeline file)
>     is updated after every build for non-MCP consumers (humans, scripts).

### `pipeline_status` (server.py:549)

Current docstring is accurate but doesn't tell the agent *when* to prefer it
over `run_pipeline`. Add a usage paragraph:

> Use this when you are iterating on the pipeline file and want a quick
> readout — "did the rebuild finish? did it error?" — without paying for a
> screenshot or blocking. Typical loop: edit file → `pipeline_status()` to
> confirm the new hash built cleanly → only call `run_pipeline()` when you
> want the screenshot back.

### `restore_version` (server.py:1290)

Current docstring is two lines and doesn't mention that it now goes through
the hot-reload path. The implementation writes the old code to
`view-<name>.py` and then calls `run_pipeline()`, so the file watcher will
fire too — harmless (same hash, dedup'd) but worth one sentence:

> Writes the historical pipeline back to `view-<name>.py` and waits for the
> rebuild. Because this overwrites the file, the watcher will also see the
> change; the coordinator dedupes by content hash so there is no double build.

## 2. `FastMCP(instructions=...)` (server.py:89)

The WORKFLOW block currently says "Add show() calls to view-main.py, then
call run_pipeline()". That phrasing predates hot reload. Insert a new section
after WORKFLOW, before ARTIFACTS:

> HOT RELOAD:
> The server watches each `view-<name>.py` and rebuilds in the background on
> every save (debounced). Builds are incremental — colormap/opacity/camera
> edits are ~free, mid-pipeline edits rebuild only downstream nodes, changing
> the data file is a full rebuild. `run_pipeline()` blocks until the build
> for the current file contents is done and returns the screenshot.
> `pipeline_status()` is a non-blocking peek — prefer it during tight
> edit loops where you don't need a screenshot every step.

Also fix step 4 of WORKFLOW: "Add show() calls to view-main.py — saving
the file triggers a build automatically; call run_pipeline() when you want
to block on the result."

## 3. New response field

`run_pipeline`'s text report should include cache stats so the agent learns
what was reused. The data is already in `BuildRecord.log` — `_build_report`
just doesn't surface it. Add one line near the timing line:

    Cache: 7 hits, 1 miss, 0 evictions  (1 node rebuilt)

This is a behavioural nudge: an agent that sees "7 hits, 1 miss" after a
colormap tweak learns the model faster than any docstring will teach it.

No new tool needed. `pipeline_status` already covers the "is it building?"
case; a `wait_for_build(timeout=)` variant would just be `run_pipeline` with
a knob. Resist adding it.

## 4. Removable tools

Nothing to remove. `restore_version` still earns its keep — writing the file
and going through the watcher is fine. `list_versions` is unchanged.
`run_pipeline` cannot collapse into `pipeline_status` because the agent
genuinely needs the blocking + screenshot path after writing a fresh file.

The one near-call: `pipeline_status` returns plain text, not JSON, despite
the docstring claiming "JSON-formatted". Either fix the docstring or return
the JSON the status file already contains. The status file is the source of
truth; having the tool return its contents verbatim would also let agents
and external scripts share one schema.
