# The DAG as the Key Representation

*Design reflection — April 11, 2026*

*This document sketches one possibility for VisLang's architectural
center of gravity: treating the content-hashed DAG produced by
executing a pipeline file as the primary representation that both the
runtime and a future compiler work on. It is framed as an alternative
to the method-dispatch framing that tracked-execution currently
implements, not as a replacement for work that has already shipped.
The alternative may realize the "spec as a communication medium
between human and agent" goal more cleanly than the current direction,
but it comes with constraints and costs that deserve upfront
examination. This document is for thinking with, not for building
from.*

## The insight in one sentence

The pipeline file is a DAG constructor; the DAG is the spec; the
compiler and runtime consume the DAG rather than the source.

Everything downstream in this document falls out of taking that
sentence literally.

## Where this came from

Three threads converge on this framing:

1. **Tracked-execution** (`experiments/tracked-execution/`) built
   content-addressed caching for PyVista pipelines. Its proxy layer
   intercepts method calls, hashes operations by their inputs, and
   caches results. The DAG it builds is currently framed as a *cache
   index* — a data structure that makes re-execution fast — rather
   than as an artifact in its own right.

2. **The workspace layer design**
   (`2026-04-10-workspace-layer-design.md`) extended tracked-execution
   with an upper vocabulary for TB-scale data management: workspace
   handles, stats queries, extract verbs, working subsets, parameters,
   sweeps. The upper vocabulary is declarative in spirit but the doc's
   API shape still mixes "what to compute" with "when and how to
   schedule it." The author is responsible for promoting expensive
   operations into the `ws.extract.*` namespace and for managing the
   working subset explicitly.

3. **The declarative-spec thread** (recent conversation) asked
   whether the visualization spec and the execution strategy could be
   cleanly separated, with the spec acting primarily as a
   communication medium between human and agent. The motivating
   observation was that scheduling concerns — which subset to render,
   what to cache, what to approximate, when to sweep — are
   implementation details the author should not have to reason about
   while describing the visualization they want.

The DAG-as-IR framing is the synthesis of these three. Tracked-
execution already builds the DAG. The workspace vocabulary can be
expressed as DAG node types rather than as eager dispatches. The
declarative-spec goal is delivered by making the DAG the spec and
letting a compiler plan from it.

## What "the DAG is the spec" means precisely

A pipeline file is ordinary Python. It runs top to bottom in a
restricted namespace. Every function or method call the file makes
records a **node** in a directed acyclic graph. Nodes name operations
(`read`, `threshold`, `isosurface`, `percentile`, `color_scale`,
`show`); edges name data dependencies (operation A consumes the
output of operation B). Each node has a **content hash** computed
from its operation, its arguments, and the hashes of its inputs.
Hashes are stable across runs and machines for the same structural
spec.

Critically, **no call eagerly computes a result**. Calling
`mesh.threshold(500, scalars="temperature")` does not run the VTK
threshold filter. It records a `Threshold` node whose inputs are the
`mesh` node and the literal arguments, and returns a lazy handle that
other calls can reference. The pipeline file's job is to build the
DAG, not to produce visuals.

At the end of the pipeline file's execution, the result is a **DAG
object**: a finite, hash-indexed, structurally complete description
of the visualization. This object is what the compiler and runtime
consume. It is the spec.

Two things that the DAG is *not*:

- **It is not the source text.** The source is a convenient way to
  build the DAG, but two different source files that build the same
  DAG are equivalent from the compiler's point of view. Renaming
  variables, reordering independent calls, factoring out helper
  functions — none of these change the DAG.

- **It is not an execution trace.** The DAG records *what should
  happen*, not *what did happen*. Execution is the compiler's concern.
  The same DAG compiled against different workspace states or different
  latency budgets produces different execution plans but is the same
  spec.

## Benefits

### Syntax becomes a front-end concern, not an architectural one

Under the DAG-is-spec framing, the question of which authoring syntax
VisLang should adopt — PyVista-flavored method chains, nested builders
like Vega-Lite, grammar-of-graphics-flavored `+` composition, JSON
dicts, a visual editor — reduces to "which front-end builds the DAG
most comfortably for the author." All of these are valid front-ends,
and more than one can coexist if useful. The compiler does not care
about source syntax; it consumes a DAG.

This dissolves a design question that has been recurring across
multiple reflections. The earlier grammar-of-graphics doc
(`2026-04-10-grammar-of-graphics-3d.md`) argued for a custom GoG-
flavored DSL. The follow-up (`2026-04-10-gog-ideas-within-pyvista.md`)
walked that back in favor of PyVista-subset with helper libraries.
The DAG framing says both are correct in their domain: the choice of
surface syntax is an ergonomic question about what the agent and
human find clearest to read and write, not an architectural question
about what the system can express or optimize.

The near-term answer is still probably "PyVista-subset front-end,"
because the agent's PyVista fluency from training data is the
project's single biggest asset. But the decision is now reversible
and additive rather than foundational.

### Hash-consing gives diffs, identity, and caching for free

Content-addressed DAG nodes give VisLang three things at once that
are otherwise separate concerns:

- **Structural diffing.** Two runs of a pipeline file produce two
  DAGs. Nodes present in both with matching hashes are unchanged;
  nodes with the same position but different hashes have changed;
  nodes present in one and not the other are added or removed.
  This diff is independent of variable naming, comment changes,
  source reordering, or helper-function refactoring — only the
  operations and their arguments matter.
- **Cross-session identity.** A node's content hash is the same
  whether computed yesterday or today, on one machine or another,
  provided the pipeline's structural content is the same.
  Cached results, persistent artifacts, and sweep records all key
  off this hash without needing a separate identity concept.
- **Incremental recomputation.** When the pipeline file changes,
  the new DAG shares subtrees with the old DAG exactly where the
  operations are unchanged. The compiler reuses plan decisions and
  cached results on the shared subtrees and only replans the
  changed regions.

The earlier conversation leaned on variable names as the anchor
for diffs, info-view lookups, and LSP hover. That argument was
structurally weak: tracked-execution's existing implementation
shows that hash-consed DAG nodes already give stable identity
without naming. Names remain useful for *presentation* — "the
`wood` layer changed" reads better than "node `a7f2...` changed"
— but they are a UX affordance on top of DAG identity, not a
mechanism for it.

### Spec-as-data lands on the DAG, not on the source

A recurring argument for custom DSL formats (JSON, Vega-Lite-style
dicts) is that they let downstream tools manipulate specs as
structured data: programmatic edits, templates, merges,
transformations, storage, transport. The earlier GoG-within-PyVista
reflection dismissed this by saying "Python's AST is enough." The
DAG framing gives a cleaner answer: the DAG itself is the
structured data, and it is a much smaller and more closed thing
than the Python AST it was built from.

Every downstream operation that wanted spec-as-data lands on the
DAG:

- **Serialization.** The DAG is a finite collection of typed nodes
  with hashable arguments. Serializing it to JSON or a protobuf is
  mechanical.
- **Transformation.** Optimizations, simplifications, and rewrites
  happen on the DAG. The rewrite rules are typed over node kinds,
  not over Python syntax.
- **Template and merge.** Two DAGs can be merged by matching nodes
  on structural position; parameterized DAGs can be instantiated by
  substituting leaves.
- **Storage and transport.** A DAG can be sent to another machine
  or stored in a database without needing to ship Python source.

The authoring surface stays Python because Python is what the agent
writes. The manipulation surface is the DAG because the DAG is what
tools reason about. These are different surfaces for different
audiences and they do not need to be the same format.

### Multiple front-ends can coexist

Once the DAG is the canonical representation, additional front-ends
become additive rather than competitive. A non-exhaustive list of
plausible front-ends over the same DAG:

- **Python PyVista-subset** (the likely default) — what the
  current tracked-execution proxy produces.
- **Python GoG-flavored builders** — for authors who prefer
  `visualization(layers=[...])` nesting.
- **JSON spec format** — for external tools, web viewers, or
  cross-language interop.
- **Visual editor / notebook cells** — dragging representations
  onto a canvas, editing encodings in a side panel, with the
  canvas writing the DAG directly.
- **Reverse engineering from existing PyVista scripts** — a tool
  that translates ad-hoc PyVista code into a tracked DAG for the
  compiler to reason about.

Each front-end is a bounded translation problem: read something the
author wrote, produce DAG nodes. They are independent of each other
and of the compiler. Adding a front-end never requires changing the
compiler or the runtime.

### The compiler sees structured intent, not Python

When the compiler's input is a DAG rather than Python source, its
job gets meaningfully easier. It does not need to walk an AST,
reason about variable scoping, understand Python's evaluation
order, or track which intermediate values are mesh-valued. It
receives a typed graph of operations with known inputs and outputs.
Rewrites, cost models, plan enumeration, and dependency analysis
all operate on this graph with standard compiler-engineering
techniques. Reasoning about Python-as-Python is work the front-end
does once during DAG construction; the compiler never has to
revisit it.

This is the same reason LLVM can support many source languages
with a single optimizer: the IR is where the compiler lives, and
the source languages are translation problems that happen before
the compiler sees anything.

## Constraints

The benefits above are real but they are not free. They depend on a
tight contract between the pipeline file and the DAG: the file must
be a pure, terminating, side-effect-free DAG constructor. This
section names what that contract requires, why each clause is there,
and what it rules out.

### DAG construction must be pure

Every operation the pipeline file records as a DAG node must be a
mathematical function of its declared inputs: same inputs, same
output, no hidden state. This is the same purity contract tracked-
execution already depends on for caching correctness.

What this rules out:

- Operations that read hidden state on the mesh (e.g., `threshold()`
  with no `scalars=` argument, which silently uses the mesh's
  currently-active scalars).
- Operations with global-state side effects (mutating a shared
  configuration, registering a callback, incrementing a counter).
- Operations whose output depends on wall-clock time, random seeds,
  environment variables, or filesystem state not captured in the
  node's inputs.

Tracked-execution's `PURITY-ANALYSIS.md` catalogs three known hazards
of this form in the current PyVista surface. The DAG framing makes
these hazards harder to ignore, because they become correctness bugs
at the spec level rather than just caching inconsistencies.

### DAG construction must terminate

Executing the pipeline file has to produce a finite DAG in bounded
time. The compiler needs a finished DAG to plan against; a file
that loops forever or recurses unboundedly never hands the compiler
anything.

What this rules out in practice:

- `while` loops over computed conditions.
- Recursive helper functions whose base case depends on computed
  values.
- Generators or iterators driven by runtime data.

What remains valid:

- `for` loops over static collections (`for v in [800, 1200]: ...`).
- `for` loops over declared parameter ranges (`for t in param("time",
  range(100)): ...`).
- Bounded helper functions that build a fixed number of DAG nodes.

### No data-dependent control flow

This is the most user-visible constraint and deserves its own
treatment. The pipeline file may not branch on the computed value
of any DAG node. Statements like

```python
if mesh.n_points > 1_000_000:
    show(mesh.decimate(0.5))
else:
    show(mesh)
```

demand that `mesh.n_points` be computed during DAG construction,
which violates purity and eagerness. The agent or human will want
to write code like this and it will not work as written.

Three escape routes exist, in increasing order of power:

1. **Hoist the decision into a declared parameter.** Replace the
   condition with `param("decimate", default=False)`, letting the
   author or compiler choose. The structure of the DAG is then
   fixed at construction time; only the parameter value varies.

2. **Express the branch as a DAG-level conditional node.** A
   `switch` or `when` node whose predicate is itself a DAG node
   (e.g., `when(mesh.n_points > threshold, then=..., else=...)`).
   The compiler resolves these at plan time, possibly reducing
   them to a single branch once the predicate is known. This adds
   complexity to the compiler but preserves expressiveness for
   cases the author genuinely cannot decide statically.

3. **Drop to `vtk_escape` for the entire sub-pipeline.** Wrap the
   offending logic in an opaque block whose input is a DAG node
   and whose output is another DAG node. The escape is cached by
   the function's source hash, so it still participates in the
   DAG, but its internals are opaque to the compiler.

Choosing among these is a language-design question. Hoisting to
parameters is cleanest when it works. DAG-level conditionals are
the most general but bear a real implementation cost. `vtk_escape`
is the pragmatic backstop for anything else.

The error messages when authors hit this constraint have to be
exceptionally good. The natural instinct is to write an `if`; the
system needs to explain why it cannot work and offer a concrete
rewrite. This is a place where the restricted-Python character
will bite hardest.

### No side effects during DAG construction

The pipeline file runs once per edit to build the DAG. During that
run, it must not:

- Print to stdout or stderr (the compiler is the one that reports
  status, not the file).
- Read or write files outside of declared `read()` operations.
- Make network calls.
- Mutate live objects across iterations.

These restrictions exist partly for purity (so two runs of the same
file produce identical DAGs) and partly so DAG construction stays
fast. A file that triggers I/O or heavy computation during
construction forces the compiler to wait on things that have
nothing to do with the spec.

### Parameters must be declared, not computed

A declared parameter — `param("timestep", range=range(100),
default=50)` — is a named slot in the DAG whose range is a static
literal. The compiler sees the slot, knows its range, and can sweep
over it, expose it as a slider, or fix it at a specific value.

A computed parameter — `param("timestep", range=range(dataset.n_timesteps))`
— would require evaluating `dataset.n_timesteps` during DAG
construction, which violates purity. The fix is either to make the
range a literal (the author knows there are 100 timesteps) or to
let the compiler inject the range after reading the workspace
manifest (a "late-bound parameter" concept that requires more
design).

The cleaner pattern, probably, is that parameter ranges may
reference *workspace-level constants* (timestep count, field list,
member count) that the compiler injects from the manifest before DAG
construction runs. This keeps construction pure while still letting
parameters adapt to the dataset. Working this out is an open
question flagged later in this document.

### The whitelist is the operational form of the constraint

Tracked-execution already enforces much of this via its method
whitelist. The whitelist is not a separate safety mechanism bolted
onto Python; it is the operational expression of "this file builds
a DAG and does nothing else." The restriction to whitelisted
methods, plus the restricted namespace (no imports, no filesystem,
no arbitrary builtins), plus the purity checks are the full
implementation of the purity/termination/side-effect contract.

The DAG framing makes the whitelist's purpose clearer. Today it
reads as "these are the PyVista operations we know how to cache
safely." Under the DAG framing it reads as "these are the operations
that may appear as nodes in the DAG." The first is a cache
consistency argument; the second is a language-definition argument.
They have the same practical content, but the second is the more
honest framing and it guides future whitelist decisions better.

## Relationship to tracked-execution

Tracked-execution already implements most of the machinery this
framing requires. Reading its module layout through the DAG-is-spec
lens, almost every existing component has a role in the new picture,
and the delta is a reinterpretation plus targeted extensions rather
than a rewrite.

### What transfers directly

- **`TrackedProxy`** (`proxy.py`) is the DAG constructor. Every
  attribute access and method call on a wrapped object records a
  node. This is exactly the contract the spec layer needs.
- **`dispatch()`** (`dispatch.py`) is the hashing and interception
  point. It already checks the whitelist, computes content hashes,
  and returns proxies for results. The content-hash primitive
  (`stable_hash`) is the identity function the DAG framing depends
  on.
- **`DAG`** (`core.py`) is already a content-hash-keyed collection
  of live results. Under the spec framing, it becomes the primary
  output of pipeline file execution rather than a cache index.
- **The whitelist** (`whitelist.py`) is the operational form of the
  pipeline file's purity/termination/side-effect contract. Its
  enforcement semantics stay the same; only the *framing* changes.
- **`vtk_escape`** is the opaque-block mechanism the constraints
  section above names as the backstop for anything the compiler
  cannot plan directly. No changes required; its role becomes
  clearer.
- **`execute_pipeline`** is the DAG constructor's entry point. It
  runs a restricted-namespace script and produces the DAG. Under
  the new framing its return value is the spec artifact, not a
  side-effectful render.
- **`SceneReconciler`** is a runtime component that takes the DAG's
  `show` nodes and reconciles them with a live Plotter. Its role is
  unchanged; it is one of several runtime backends the compiler can
  target.

### What needs reframing without code changes

Several things that tracked-execution thinks of as "caching" become
"spec construction" under the new framing, with no behavioral change
needed:

- **Per-run GC of the DAG.** Today tracked-execution evicts DAG
  entries that are not touched during a run. Under the spec framing,
  this is how the new DAG supplants the old: the set of nodes
  touched during the run *is* the new spec, and anything else is
  genuinely stale.
- **`inspect_pipeline` and `dag.names`.** These are read-only views
  over the constructed DAG. Under the spec framing they become
  tools for querying the spec, feeding LSP hover, and populating
  info-view panels.
- **The purity warnings.** Today these are framed as caching
  correctness hazards. Under the spec framing they are spec
  correctness hazards — the same fix, but with a clearer argument
  for why it matters.

### What needs actual extension

The gap between today's tracked-execution and the DAG-is-spec
framing is not large but it is real:

- **Render, stats, extract, and param operations must become
  deferred DAG nodes.** Today some operations at the edges of a
  pipeline execute eagerly: `show()` records an actor entry that
  gets rendered, screenshot captures happen immediately, stats
  computations run directly on materialized meshes. Under the spec
  framing, all of these become DAG nodes whose execution is the
  compiler's responsibility. `show` becomes a `ShowLayer` node;
  `screenshot` becomes a `Screenshot` terminal node; stats become
  `StatsQuery` nodes consumed by other nodes.
- **A plan phase between DAG construction and execution.** Today
  the DAG is executed depth-first as it is constructed, with cache
  lookups providing the laziness. Under the spec framing, DAG
  construction finishes first and produces a complete graph; the
  compiler plans from the complete graph; the runtime executes the
  plan. This is a genuine new phase in the system, not a
  reinterpretation.
- **Richer node types.** Today the DAG nodes are mostly "PyVista
  method call with arguments." Under the spec framing, the DAG
  needs node types for scales, encodings, compositions, parameters,
  workspace handles, stats queries, and extract requests. Each
  requires a typed definition, not just a method name. This is the
  vocabulary-design work flagged in the open questions below.
- **Persistent DAG identity across sessions.** Today the DAG is
  in-memory and rebuilt on each run. Under the spec framing, the
  DAG (or key parts of it) wants to persist so that sessions can
  resume, plans can be reused, and sweep records can reference
  spec versions by hash. This is an extension to how `DAG` stores
  itself, probably using the workspace artifact as the persistence
  layer.

None of these extensions requires discarding existing code. Each is
additive or reinterpretive. The tracked-execution investment pays
off in this framing as much as it pays off in the workspace-layer
framing — arguably more, because the DAG framing makes the existing
content-hash machinery load-bearing for the whole system rather
than just for caching.

## The LLVM analogy

It is worth being explicit about the LLVM parallel because it
clarifies which design questions belong at which layer.

LLVM's architecture has three tiers: source languages, IR (LLVM
bitcode), and target backends. C, C++, Rust, Swift, and many others
compile to the same IR. The optimizer works entirely on IR. Backends
for x86, ARM, WASM, and so on consume optimized IR and produce
target code. The IR is the narrow waist: it is the only interface
that the optimizer and backends agree on, and the source-language
authors and the target-backend authors work independently against
it.

VisLang's analog under the DAG framing:

| LLVM | VisLang (DAG framing) |
|---|---|
| Source languages (C, Rust, Swift) | Front-ends (PyVista-subset, nested builders, JSON, visual editor) |
| LLVM IR | The content-hashed DAG |
| Optimizer | The compiler / planner |
| Optimization passes | Rewrites on the DAG (simplification, common-subexpression elimination, pyramid-level selection, approximation insertion) |
| Target backends (x86, ARM) | Runtime backends (PyVista Plotter, Trame viewer, batch sweep executor, feature-DB writer) |
| Bitcode serialization | DAG serialization to JSON or protobuf |
| `clang -O2` vs `clang -O0` | The compiler's latency-budget and fidelity settings |

The parallel is strong enough to borrow LLVM's architectural
wisdom:

- **The IR is the contract.** Changes to the front-ends should not
  require changes to the compiler or runtime, and vice versa. The
  DAG node vocabulary is where the interface discipline happens.
- **The optimizer is the hard part.** LLVM spent years making the
  optimizer good. VisLang's compiler will be similarly the longest
  running and most intellectually demanding component.
- **Backends are interchangeable.** The same DAG should be able to
  target a live Plotter for interactive work, a Trame viewer for
  remote rendering, a batch executor for sweeps, or a headless
  screenshotter for CI, without the DAG or the front-end changing.
- **IR debugging is a first-class concern.** LLVM has `llvm-dis`,
  `opt -print-after-all`, and extensive diagnostic tooling for the
  IR. VisLang will want analogous tools: DAG dumps, plan
  diagnostics, per-node cost reports.

The analogy is not perfect. LLVM's IR is a low-level imperative
instruction set; VisLang's DAG is a higher-level operation graph
closer to relational algebra or dataflow. But the architectural
pattern — narrow IR waist between many front-ends and many backends,
with the compiler living in the middle — is the same and is what
makes both systems tractable at scale.

## Open questions

These are the design questions the framing does not itself answer.
Most of them need prototypes or a concrete vocabulary pass before a
confident answer is possible.

### What is in the DAG node vocabulary?

The most consequential open question. The set of node kinds the DAG
supports defines what visualizations can be expressed and how much
work the compiler can do.

At minimum the vocabulary probably needs:

- **Data nodes.** Dataset references, field references, workspace
  handles, timestep/member selectors.
- **Transform nodes.** Thresholds, clips, slices, gradients, derived
  fields, resamplings, smoothings.
- **Representation nodes.** Isosurface, volume, streamlines, glyphs,
  slice, outline, surface — the 3D analog of ggplot2 geoms.
- **Encoding nodes.** Color scales, opacity scales, size mappings,
  shading properties. Possibly with separate `Scale` and `Encoding`
  node kinds since scales are reused across layers while encodings
  bind to specific representations.
- **Composition nodes.** Layers, facets, overlays, scenes.
- **Parameter nodes.** Declared variables with ranges, defaults,
  types, and binding affordances.
- **Stats nodes.** Percentile, range, histogram, spatial extent,
  distribution shape. These are consumed by encoding and transform
  nodes (e.g., a color scale whose range is "the 5th-95th percentile
  of temperature" references a stats node).
- **View nodes.** Camera, projection, background, lighting.
- **Terminal nodes.** Render, screenshot, export, animate — the
  nodes that tell the compiler what the pipeline's output is.

The right level of decomposition is not obvious. Should a streamlines
representation be one node or several (seed generation, integration,
tube filtering, mapping)? Should an encoding be a bundle or a
collection of scales that the compiler binds together? Should stats
be their own node kind or just a sub-form of transforms? Each
decision affects how the compiler can reason about the graph.

A practical way forward is probably to define a minimal vocabulary
sufficient for the fire-sim and bonsai examples and grow from there,
rather than designing the full vocabulary up front.

### How are conditionals expressed?

The constraint that the DAG be built without data-dependent branching
pushes conditionals out of the surface language and into one of three
places: declared parameters, DAG-level `when` nodes, or opaque escape
blocks. Choosing the right default — and whether all three are
supported or only a subset — is genuinely hard.

A plausible default: parameters first, opaque escape as the backstop,
DAG-level conditionals deferred until a concrete use case forces
them. This keeps the compiler simple initially.

### How do late-bound parameters work?

A parameter like `param("timestep", range=range(dataset.n_timesteps))`
wants to adapt its range to the workspace without violating the
purity of DAG construction. Several approaches exist:

- **Workspace-level constants** injected into the namespace before
  the pipeline runs, so `workspace.n_timesteps` is a literal by the
  time `param(...)` sees it.
- **A `workspace_param` node kind** that the compiler resolves
  against the workspace manifest at plan time. The DAG records the
  intention ("timestep parameter, range from workspace"); the plan
  records the resolved range.
- **Forbid late-bound parameters entirely** and require literal
  ranges. Author has to copy the timestep count manually.

The middle option is probably right but it introduces a node kind
whose "value" depends on external state, which complicates the
purity story. Worth careful thought.

### Is the DAG visible to the author?

Two models are possible:

- **Hidden DAG.** The author writes front-end code; the DAG is an
  implementation detail the compiler and tooling manipulate. The
  author never sees DAG dumps directly; tools surface DAG
  information through friendlier presentations.
- **Inspectable DAG.** The author can ask the system for a DAG dump,
  the compiler's plan, or a per-node cost report. The DAG is a
  concept the agent knows about and can reason about.

For an LLM agent collaborator, the inspectable model is probably
better: the agent can read a DAG dump directly, notice structural
issues, and propose edits at the DAG level when the source-language
surface is awkward. For a human scientist, the hidden model is
friendlier. Supporting both (the DAG is inspectable when asked but
not required for normal work) is likely the right answer, and the
presentation tooling is where the UX distinction lives.

### How fine-grained are cache / plan reuse boundaries?

When the pipeline file changes, some nodes are unchanged (same
hash), some are changed (different hash with same structural
position), some are added, some are removed. The compiler wants to
reuse plan decisions and cached results on unchanged nodes and only
replan the changed regions.

This is easy in the degenerate cases (pure add, pure remove) and
harder in the interesting ones (a parameter tweak that changes one
argument of one leaf node, cascading hash changes up the spine of
the DAG). The question is how much plan reuse the compiler can do
when hashes change up a chain: does it replan the whole chain, or
can it recognize that the *structure* is stable and only the
*arguments* moved?

Probably the answer is "both" — the compiler has two notions of
identity (structural position and content hash) and uses the first
for plan reuse and the second for cached-result reuse.

### How does debugging work across the DAG/plan boundary?

When a visualization looks wrong, the author needs to trace the
problem. Is it in the spec (wrong node kind, wrong argument)? In
the plan (bad approximation choice, wrong pyramid level)? In the
runtime (VTK filter bug, wrong rendering state)? The DAG framing
introduces a layer boundary that debugging has to cross.

The mitigation is probably to report problems at the right layer:
spec-level errors show the DAG node that caused them, plan-level
errors show the plan decision, runtime errors show the VTK state.
Each layer's error messages name the layer explicitly so the author
knows where to look. This is a nontrivial investment but it is the
price of the layering.

## Risks

### The termination constraint is user-visible

Authors will write `if` and `while` with computed conditions
because that is what Python is for. The first time they do, they
will hit a hard error. The error needs to explain, concretely and
actionably, what to do instead. If the error is bad, the layering
feels brittle and authorial.

### The compiler is still hard

The DAG framing makes the compiler's *input* cleaner. It does not
make the compiler's *job* easier. Picking the right pyramid level,
the right approximation, the right sweep granularity, the right
cache reuse — these are genuinely hard questions and the DAG does
not answer them. The honest expectation is that the first compiler
will be dumb, and the escape-hatch mechanisms (hints, explicit
plan overrides, `vtk_escape`) have to be good enough to compensate
until it gets smart.

### The vocabulary design is load-bearing and hard to change later

Once the DAG node vocabulary is fixed and front-ends, compiler, and
runtime are written against it, changes are expensive. The
vocabulary has all the properties of an API: additive changes are
easy, semantic changes are painful. This argues for starting with
a minimal vocabulary and growing it cautiously, and for keeping
prototypes as informal as possible before committing.

### Two layers to debug, two layers to learn

Today's VisLang has one layer: the pipeline file runs and produces
a visualization. Under the DAG framing, there are three layers
(front-end, DAG, plan) and four layers including the runtime. Each
layer has its own vocabulary, its own failure modes, and its own
debugging affordances. The conceptual overhead is higher for
everyone — authors, agents, contributors. This is the price of
separation of concerns, and it is worth paying only if the
separation buys enough.

### The DAG may not be the right abstraction for all of VisLang

Some things VisLang wants to do may not fit cleanly in a DAG. In-
situ coupling, for example, has a time-varying data source that
does not map neatly onto a static DAG of operations. Streaming or
reactive patterns (where the spec updates as new data arrives) may
also fight the DAG framing. The right answer is probably to keep
the DAG framing for the batch / post-hoc case (the grant focus)
and consider alternatives for streaming as and when they become
relevant.

### Performance of DAG construction and hashing could matter

Hashing every operation, wrapping every result in a proxy, and
maintaining a DAG add overhead to every call. Tracked-execution
has shown this is tractable for typical pipelines, but it is worth
measuring carefully for large pipelines with thousands of nodes.
If construction cost grows faster than expected, optimizations
(incremental reconstruction, subtree memoization, lazy hashing)
may be needed.

## What this is and is not

### What this is

- **A reinterpretation of what tracked-execution already builds.**
  The DAG is the spec; tracked-execution is already constructing it.
  The extensions needed to make it the full project's central
  representation are additive, not disruptive.
- **A separation of authoring syntax from compiler and runtime
  concerns.** Once the DAG is the IR, syntax is a front-end choice
  rather than an architectural commitment, and multiple front-ends
  can coexist.
- **A foundation for the declarative spec goal.** If the DAG is
  where the compiler lives, the pipeline file becomes a DAG
  constructor whose job is to express intent, not to schedule or
  execute work. This realizes the "spec as communication medium
  between human and agent" aspiration more fully than a method-
  dispatch surface does.
- **A framing that makes spec-as-data, diffing, caching, and
  multiple backends land at the same layer.** All four of these
  are concerns the DAG absorbs. They are not separate problems
  that need separate solutions.
- **Compatible with the workspace artifact.** The on-disk artifact
  described in `2026-04-10-workspace-layer-design.md` is the
  persistence layer for this framing; the two are complementary
  rather than alternative.

### What this is not

- **Not a finished language design.** The DAG node vocabulary is
  an open question; this document does not propose a specific one.
- **Not a commitment to a specific front-end syntax.** PyVista-
  subset is the likely default, but the framing does not require
  it.
- **Not a claim that the compiler will be easy.** Moving the
  compiler's input from Python source to a typed DAG makes it
  tractable, not trivial.
- **Not an argument against tracked-execution's current direction.**
  Most of the existing code carries forward; the change is in how
  it is framed and what it is extended to support.
- **Not validated by implementation.** This is a framing
  reflection. Whether it holds up under concrete use needs
  prototypes and measurement.

## Closing note

The DAG-as-IR framing is a compression: it names a pattern that
was already implicit in tracked-execution, the workspace design,
and the declarative-spec conversation, and it makes that pattern
explicit so the rest of the design can be organized around it.
Nothing in the framing is new in any deep sense. What is new is
the decision to take it seriously as the project's architectural
center rather than treating the DAG as an implementation detail of
caching.

The companion reflection (`2026-04-11-declarative-spec-workspace.md`)
works out what the workspace layer design looks like when rebuilt
on top of this framing, with the spec layer genuinely free of
implementation concerns and a compiler taking on the scheduling
responsibilities that the workspace doc originally assigned to the
author.
