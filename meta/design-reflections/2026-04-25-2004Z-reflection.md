# Design Reflection — Where the project actually is

Date: 2026-04-25
Focus: integrating direction from the post-paper feedback wave. Not a
line-by-line code audit. The two annotations-redesign reflections from
earlier today already cover that local territory.

## Section 1: Code quality (brief)

Nothing structurally new since the April 6 code-quality pass. The
mechanical wins (auto-populated DSL namespace, unified
`_auto_opacity`, shared scalar-bar builder, separated 2D overlay
actors, MCP-protocol tests, stateful integration tests, legacy global
state removed) all landed. `server.py` is still the elephant: 2,264
lines, 25 `@mcp.tool` handlers + pipeline execution + DSL doc
strings + session state. The split-into-modules item is `[~]` in the
backlog and was deliberately deferred — sensible, since the tool
surface is still in flux. Don't split until the tool-set stabilizes;
otherwise we'll be moving the same code twice.

The one structural concern that *did* surface in this feedback cycle
is in `dsl.py`, not `server.py`: the empty-output diagnostics at
`filters.py:629–703` are an `if/elif` chain, the wrapper-vs-build
error channels are split (see "unified error reporting" feedback),
and downstream builders crash on failed upstream nodes
(see "cascade leak" feedback). These are diagnostic-quality issues,
which I'll treat as design questions in section 3.

## Section 2: API surface

The April 6 reflection counted ~45 tools. Today it's **25**. That's a
real accomplishment — `get_array_info`/`get_node_info`/`get_bounds`
folded into `describe_data`, `suggest_opacity`/`get_actor_info`/
`render_chart`/`quick_start`/`list_actors` removed, mutation tools
trimmed, redundant query tools removed, `set_pipeline → run_pipeline`
renamed. The shape is much closer to the design intent: data-aware
query tools + a small mutation surface + reference tools.

**Tool-shape observations:**

- The 25 tools are reasonably uniform: `node`/`field`/`file_path`
  parameter naming is consistent across query tools; mutation tools
  return `list[str | Image]` for screenshot bundling; query tools
  return strings.
- `describe_data(node="", file_path="", field="")` is the right shape
  — three roles (post-load summary, pre-load preview, single-field
  rich stats) merged into one tool with mode-selecting parameters.
  Good model for future merges.
- The remaining mutation tools (`set_camera`, `set_window_size`) are
  legitimate exceptions — camera state is interactive and shouldn't
  live in the pipeline file. The "Do With Human / Remove mutation
  tools" item is partially done; what remains is genuinely justifiable.

**DSL-shape observations from the dsl-design-critique feedback:**

The DSL surface (the *forms*, not the *MCP tools*) has accumulated
inconsistencies that the tool-count reduction didn't touch:

- snake_case wrapper args mixed with CamelCase VTK passthrough
  (`contour(input=data, ContourBy=..., Isosurfaces=...)`)
- `curl(vector_field=..., vector=True/False)` is the odd one out:
  positional-style first arg, plus a bool toggling output rank
- `clip` vs `clip_sphere` vs `clip_box` have inconsistent
  `inside_out` defaults
- `extract_grid` and `extract_region` overlap with different argshapes
- `source` / `load` / `raw_source` are three doors to "get data in"
- `extract_region` raises eagerly while everything else collects
  errors — wrapper-vs-build channel split

These are real, not stylistic. They mostly reflect that the DSL grew
filter-by-filter without a periodic style pass. The MCP tools got
that style pass; the DSL forms didn't.

**Property-typo opacity** (#10 in dsl-design-critique) is the
highest-leverage local fix on the DSL side: `create_vtk_filter` could
check `hasattr(vtk_class, "Set" + key)` and raise structured errors
listing valid properties. This is what bit the agent in the
cascade-leak session — a typo'd `ScalarArrays` on `vtkGradientFilter`
silently no-op'd, then the empty downstream output produced four
different error idioms.

**Instructions string accuracy** is good post-cleanup. `MUTATION_TOOLS`
auto-feeds `_ALL_TOOLS` and the instructions, which catches drift
mechanically. `gen_docs.py` errors on stale DSL form names. The
discipline is paying off.

**Reasonable next direction on tool surface:** stop trimming, start
making the *output* of build reports cheaper to read (terse mode for
unchanged nodes, see backlog) and the *input* validation richer
(field schemas on NodeRef, see section 3).

## Section 3: Design direction

### Where we are

The mechanical phase is mostly over. Tool count, naming, mutation
removal, dead-code, test coverage, doc generation — the obvious wins
are taken. The recent commits trend confirms it: the last two weeks
were *small* changes (axes form, threshold-first guidance, scalar-bar
redesign, isosurface coloring tip, annotations DSL form), not new
capability bolts. That's healthy. It means the system is in
maintenance/polish phase relative to its core, and the strategic
question is "what's the next layer of capability."

The five April-25 feedback entries are remarkably coherent on what
that next layer is:

1. **dsl-design-critique** — the DSL itself has vibecode artifacts
   that should be cleaned up; bigger question is whether to rebuild
   on PyVista.
2. **cascade-leak** — one upstream error → four downstream error
   idioms; build-phase contract is leaky.
3. **unified-error-reporting** — wrapper-raise vs build-status is an
   accidental boundary; should collapse to one channel.
4. **noderef-output-schema** — field references are bare strings
   untethered to nodes; typos caught only after VTK runs.
5. **multi-frame-visual-feedback** — `camera_orbit` is metacognitively
   triggered and under-used; auto-included overview thumbnails sidestep
   the trigger problem.

The first four are all about **error/feedback quality during pipeline
authoring**, viewed from different angles. The fifth is about **visual
feedback richness** post-build. Both are downstream of the same
underlying recognition: the agent's per-turn cost is dominated by
*understanding what just happened*, not by typing the next line. We
went a long way reducing the cost of typing (DSL clarity, tool
simplicity, suggestion tools); now the bottleneck is understanding.

### What's been validated by recent feedback

- **The deferred-graph + serialized `view-*.py` + per-node feedback
  architecture is the right frame.** All five feedback entries
  reinforce it (none challenge it). The dsl-design-critique
  explicitly identifies it as the differentiator, not the DSL surface.
- **Reader caching and rebuild-on-each-call is fast enough.**
  The reconciler work is a polish item, not a necessity.
- **MCP tool simplification works.** 45 → 25 didn't break anything
  and is repeatedly cited as nicer than viznoir / PyVista's surface.
- **`describe_data(field=)` mode-merging is the right pattern.** The
  backlog has a parallel item to do this for `get_statistics`/
  `get_field_summary`/`get_node_info` — this should land.

### What's been invalidated or complicated

- **"All errors at once" is partly aspirational.** The cascade-leak
  feedback shows that the build-phase aggregation breaks under
  realistic chains. The single-error-channel-via-status proposal in
  unified-error-reporting is the right direction.
- **Bare string field references are a real cost.** Multiple sessions
  hit `Vorticity` capitalization confusion or magnitude/vector
  schema confusion. The agent recovers in one extra turn, but that
  turn happens *every time the typo gets made*. NodeRef-with-schema
  is a real design question, not just engineering.
- **Tool-discoverability vs trigger-recognition is a different
  axis than tool count.** `camera_orbit` exists, agents don't reach
  for it. Reducing tool count further won't help; *making the right
  tool the default behavior* (auto-include overview, auto-scalar-bar
  for `color_by`) might.

### Strategic direction — what should come next

In rough priority order:

1. **Fix the diagnostic spine.** The cascade-leak and
   unified-error-reporting items are small, mechanical, and high
   leverage. They pay back on every pipeline error, which is most
   pipelines on the first build. Do these before anything else.
   Property-typo checking (#10 in dsl-design-critique) is a sibling
   in the same theme.
2. **Audit the DSL forms for the vibecode-era inconsistencies**
   (#1–#6 in dsl-design-critique). Snake_case vs CamelCase, `curl`
   signature, `inside_out` polarity, `extract_grid`/`extract_region`
   overlap, `source`/`load`/`raw_source` consolidation. None of
   these are individually large; together they are the equivalent
   of the tool-surface cleanup that we already did on the MCP side.
3. **Decide on NodeRef output schema.** This is a real design choice
   — the feedback entry itself flags the tradeoff. My read: do it,
   but scoped narrowly to the high-traffic field-accepting wrappers
   (`color_by`, `ContourBy`, `ThresholdBy`, `extract_component`,
   `field=`). Don't try to make it total. Pairs naturally with the
   `Vorticity` array-leak cleanup.
4. **Auto-inclusion of richer feedback in default responses.** This
   is the most ACI-research-interesting direction. Start with the
   overview-thumbnail experiment (low cost, easy to evaluate).
   Vega-lite-style auto-scalar-bar / diverging-colormap inference is
   the same pattern from the build-spec side: enrich the default
   output so the agent doesn't have to know to ask.
5. **Reduce `set_pipeline` output verbosity** (existing backlog
   item). Subsequent builds repeat full array lists; a terse "what
   changed" mode pairs with the reconciler work and reduces the
   per-turn context cost.
6. **Defer the bigger architectural questions** — VisLang-on-PyVista
   (#13 in dsl-design-critique), `exec`-style inspection sandbox
   (#14), reusable subgraphs (#15). All three are interesting, all
   three are several-week investments. Run a dedicated design
   reflection on each before committing. The PyVista one in
   particular needs a small prototype on one filter before any
   broader move — the feedback entry's caveat about "PyVista does
   this better" being conversation-recall is appropriate.

### Drift in VISION.md

`meta/BACKLOG.md` flags this as a "Do With Human / Medium" item and
it's accurate. Specifically:

- VISION.md Part 1 says "The MCP server exposes ~35 tools" — actual
  count is **25**.
- VISION.md lists `get_examples()` and `list_capabilities()` as
  reference tools. Both are gone — folded into `get_dsl_overview`
  and `get_dsl_reference`.
- VISION.md lists `set_colormap`, `set_opacity`, `toggle_visibility`,
  `load` under "Mutation tools." All are removed or in the process
  of removal except `load` (and even `load` is being reconsidered
  per the `start_session` idea).
- VISION.md still describes `suggest_opacity()` as a query tool —
  that was replaced by the CDF-rarity algorithm and the tool itself
  was removed.
- VISION.md does not mention the MCP-protocol tests, the
  reconciler work, or the named-views architecture as core current
  capabilities. Named views in particular is now a foundational
  feature, not a footnote.
- The architecture diagram still shows the `set_colormap`/
  `set_opacity` mutation tools.

This is the kind of drift that compounds: every new contributor reads
VISION.md to orient, and a misleading orientation costs hours of
correction. Worth a focused VISION.md refresh — but as a
**human-reviewed** edit, not an autonomous one. (Note: do not edit
VISION.md as part of this reflection.)

## Closing — Proposed backlog items, prioritized

**High priority — diagnostic spine:**

- **Fix cascade-leak in downstream builders** — uniform "skip
  descendants of failed nodes" contract enforced at the per-node
  build entry. Add `upstream` field to status. Audit specialized
  builders (`_build_extract_region_node`,
  `_build_extract_component_node`) for None-checks. *Highest-leverage
  fix in this cycle: turns four failure idioms into one, on the
  most common author-error class.*

- **Unify wrapper validation into build-phase status channel** —
  no `raise` in DSL wrappers; missing args become recorded node
  errors. One channel for the agent. Small refactor; pairs with the
  cascade-leak fix.

- **Property-typo checking in `create_vtk_filter`** — `hasattr(
  vtk_class, "Set" + key)` check with structured "unknown property
  on `vtkContourFilter`; valid: [...]" error. Half-day of work;
  catches the `ScalarArrays`-on-`vtkGradientFilter` class of mistake
  that drove the cascade-leak example.

**Medium — DSL surface cleanup:**

- **DSL form vibecode pass** — pick one: snake_case-only with
  internal mapping or explicit `vtk={...}` passthrough. Fix `curl`
  to `input=` keyword + `mode="vector"|"magnitude"` (or split into
  two wrappers). Unify `clip*` `inside_out` defaults. Drop or
  re-label `extract_grid` vs `extract_region`. Consolidate
  `source`/`load`/`raw_source`. Mirror of the MCP-tool simplification
  pass we already did.

- **NodeRef output schema (scoped)** — declare per-wrapper "what
  arrays I add/remove." Validate field-accepting kwargs at
  `interpret()` time. Don't try to be total — fall back to
  build-phase validation for `filter()` and unknown classes.
  Bonus: drop the leaked `Vorticity` array from `curl()`.

**Medium — agent-feedback richness:**

- **Auto-include overview thumbnail in build responses** — small
  low-res overview-framed image alongside the main screenshot.
  Tests the hypothesis that trigger problems disappear when
  triggering isn't required. Low cost, easy to evaluate over a
  few sessions.

- **Vega-lite-style display-property inference** — auto scalar_bar
  when `color_by` set; diverging colormap + symmetric range for
  signed fields; auto scalar_bar title from field name. Same theme
  as the thumbnail item: enrich defaults rather than rely on the
  agent to know to ask.

- **Terse `run_pipeline` output for unchanged nodes** — already
  in backlog; bump priority. Pairs with reconciler diff.

**Low — strategic / needs more design:**

- **Empty-output diagnostics → registry pattern** —
  `filter_class → diagnostic_fn`. Small refactor; unblocks broader
  coverage. Already in dsl-design-critique #7.

- **VISION.md refresh** — already in backlog. Worth doing soon
  to avoid further drift, but human-reviewed.

- **Reflection-only items (do not yet add to backlog):**
  VisLang-on-PyVista prototype, `exec`-style inspection sandbox,
  reusable subgraph macros, autonomous-exploration mode with
  attention-flagging. Each merits its own focused reflection
  before becoming an item.

The first three (cascade-leak, unified-error-reporting,
property-typo) are the highest-leverage things in this list.
Together they can probably ship in a single focused week and
will measurably improve every error-recovery loop in every session.
